# Prep Overnight — Add Context to Near-Ready Issues

Takes issues that `/zv01.5-overnight` flagged as "needs-scoping" and autonomously builds enough context (exploration + plan) so the overnight executor can run `/zv05-execute` without human input.

**When to run:** After `/zv01.5-overnight` identifies "needs-scoping" issues, or directly with issue IDs.

## Input

The user provides either:
- Specific issue numbers: `/zv01.6-prep-overnight 128 119`
- "all" or no args: fetch all Backlog/Todo issues in the project that have no exploration or plan artifacts yet

## Flow

### 1. Gather Issues

If specific issue numbers provided, fetch each via `gh issue view <number>`. Otherwise, fetch Backlog + Todo issues for AXIS Command Center project.

Filter out issues that already have artifacts:
- Grep `ai/zv/explorations/` and `ai/zv/plans/` for each issue number
- Skip any issue that already has a plan (it's already prepped)
- Skip any issue that already has an exploration (it's mid-pipeline)

### 2. Quick Triage (Serial)

For each issue, do a 10-second assessment:
- Read the GitHub issue description fully
- Does it have a clear problem statement and expected outcome? If not → skip, flag as "too vague for autonomous prep"
- Does it require product/UX decisions that can't be derived from the codebase? (e.g., "redesign the landing page") → skip, flag as "needs interactive /grill-me"
- Is it a massive epic (10+ files, new tables, complex migrations)? → skip, flag as "too large — needs daytime /zv03-explore"

Produce a shortlist of issues that are **well-specified but missing codebase context**.

### 3. Parallel Context Building

Launch **parallel subagents** (Agent tool, `subagent_type: "general-purpose"`) — one per issue (max 4 concurrent). Each agent receives:

**Agent prompt template:**
```
You are preparing GitHub issue #{ISSUE_NUMBER}: "{TITLE}" for autonomous overnight execution.

## Issue Description
{FULL_DESCRIPTION}

## Your Task

### A. Explore the codebase
- Find all files referenced in the description (verify they exist, note current state)
- Find related files by grepping for key terms (table names, component names, function names)
- Identify patterns in similar existing code (how was a similar feature built before?)
- Check for migrations, RLS policies, types, API routes, hooks, and UI components that would be affected

### B. Resolve open questions autonomously
- If the description says "TBD" or "to decide" — make the simplest choice consistent with existing patterns and document it
- If a design question can be answered by reading CLAUDE.md or existing code conventions — answer it
- If a question genuinely requires product judgment — flag it as "[NEEDS HUMAN]" and scope it OUT of the plan

### C. Write an exploration artifact
Save to `ai/zv/explorations/{DATE}-{SLUG}.md` using this format:

```markdown
# Exploration: {TITLE}
**Issue:** #{ISSUE_NUMBER}
**Date:** {TODAY}
**Prep Mode:** Autonomous (via /zv01.6-prep-overnight)

## Summary
1-2 sentences.

## Affected Files
| File | Role | Change Type |
|------|------|-------------|
| `path/to/file.ts` | Description | add/modify/delete |

## Current Patterns
How similar things work today in the codebase (so the executor follows convention).

## Decisions Made (Autonomous)
- Decision: [choice] — derived from [codebase evidence]

## Scoped Out (Needs Human)
- [NEEDS HUMAN] Item — why it can't be resolved from code alone
(If empty, write "None — fully autonomous")

## Risks
- Risk and mitigation
```

### D. Write a plan artifact
Save to `ai/zv/plans/{DATE}-{SLUG}.md` following the standard plan format from /zv04-plan:

- Phase-based with commit points
- Checkboxes for progress tracking
- Sprint Contract (FUNC, SEC, REG minimum)
- Conservative scope: only include what's clearly specified. If you scoped something out in step C, do NOT include it in the plan.

The plan must be detailed enough that `/zv05-execute` can implement it without reading the GitHub issue or asking the user anything.

### E. Return a summary
Return: { issueNumber, title, filesAffected: number, phasesInPlan: number, scopedOutItems: string[], confidence: "high" | "medium" }
```

### 4. Report Results

Show a summary table:

```
## Prepped for Overnight
| Issue  | Title                              | Files | Phases | Confidence |
|--------|------------------------------------|-------|--------|------------|
| #42    | Well-specified backend task         | 5     | 3      | high       |

## Scoped-Out Items (Need Daytime Attention)
| Issue  | Item                                              |
|--------|---------------------------------------------------|
| #42    | [NEEDS HUMAN] Whether dropdown should be multi-select |

## Skipped (Not Suitable for Autonomous Prep)
| Issue  | Title                              | Reason                          |
|--------|------------------------------------|----------------------------------|
| #43    | Vague epic                         | No clear outcome in description  |
```

### 5. Confirm

Ask the user:
> These issues now have exploration + plan artifacts. Want me to label them "overnight" in GitHub?

## Design Principles

- **Conservative scope over ambitious scope.** A narrow correct plan beats a broad wrong one. When in doubt, leave it out and flag it.
- **Derive decisions from code, not imagination.** Every autonomous decision must cite what codebase evidence it's based on (file, pattern, convention).
- **No UI/UX judgment.** If the issue involves visual design decisions, component layout choices, or interaction patterns that aren't already established — skip it or scope those parts out.
- **Plans must be self-contained.** The overnight executor reads the plan file. It should not need to cross-reference the GitHub issue or ask the user.

## Notes

- Uses the same plan format as `/zv04-plan` (Sprint Contract required)
- Uses the same exploration format as `/zv03-explore` (with "Prep Mode: Autonomous" flag)
- If an issue already has a journal in `.overnight/journals/{issue-number}.md`, read it for context from previous attempts
- Today's date: use the actual current date for file names, not a placeholder
