# Overnight Scrub — Identify Pipeline Candidates

Scrub the backlog to find issues suitable for the unattended overnight pipeline. Run this before bed to queue tonight's batch.

## Overnight Criteria

An issue is a good overnight candidate when **all** are true:

1. **Well-scoped** — clear description with concrete problem/outcome, not vague brainstorming
2. **No product decisions** — no UX choices, business logic tradeoffs, or design judgment needed mid-flight
3. **Isolated** — no dependencies on other in-progress work or pending migrations
4. **Testable** — verifiable via lint, typecheck, test, and/or build
5. **Backend-friendly** — schema/API/trigger work is ideal; UI-heavy work with design decisions is NOT

## Split Detection

If an issue has **significant backend AND significant UI**:
- Suggest splitting into two issues:
  - Backend (overnight): migration + API + triggers + types
  - UI (interactive): components, UX, visual changes
- Naming: short prefix from issue title, e.g., "DATES1: Backend — add column" / "DATES2: UI — date picker"
- Only split if backend is substantial (new tables, complex migrations, RLS changes). Trivial backend (one column, no triggers) = don't split.

## Flow

### 1. Fetch Issues

Use `gh` CLI to fetch open issues:
- Project: AXIS Command Center (or detect from CLAUDE.md)
- States: not:closed (skip in-progress — those are already being worked on)
- Sort by priority labels: `P1-urgent` → `P4-low`

### 2. Assess Issues in Parallel

Launch **parallel subagents** (Agent tool, `subagent_type: "Explore"`) — one per issue (or batch 2-3 per agent if >8 issues). Each agent receives:
- The issue ID, title, description, and priority
- The 5 overnight criteria (from above)
- Instructions to run the quick scope check below and return a verdict

**Quick scope check** (each agent runs independently):
- Are the referenced files real? (`Glob` to verify)
- How many files would change? (`Grep` for key terms)
- Is there a migration involved? (check `supabase/migrations/`)
- Does the description mention UI components, design, or UX? → flag as needs-interaction

Each agent returns: `{ issueNumber, verdict: "ready" | "preppable" | "needs-interactive" | "not-suitable", reason, splitRecommended? }`

**Verdict definitions:**
- **ready**: meets all 5 criteria, has enough detail to execute tonight
- **preppable**: nearly ready, needs `/zv01.6-prep-overnight` to build exploration/plan
- **needs-interactive**: has product/design questions → needs human feedback before execution
- **not-suitable**: vague, too large, or has blocking dependencies
- **preppable**: well-specified (clear problem + outcome) but missing codebase context — `/zv01.6-prep-overnight` can fill the gap autonomously
- **needs-interactive**: vague, open-ended, or requires product/UX decisions — needs `/grill-me`
- **not-suitable**: too large, too risky, or blocked by dependencies

Merge all agent results into the three buckets below.

### 3. Present Results

Show three buckets with a table for each:

```
## Ready for Tonight
| Issue  | Title                              | Pri | Why                              |
|--------|------------------------------------|-----|----------------------------------|
| #XX    | Clear backend task                 | ▲   | Schema-only, well-scoped         |

## Preppable — Run /zv01.6-prep-overnight to Add Context
| Issue  | Title                              | Pri | Gap                              |
|--------|------------------------------------|-----|----------------------------------|
| #XX    | Well-specified but needs codebase context | —  | Missing affected files, no plan  |

## Needs Interactive Scoping (/grill-me)
| Issue  | Title                              | Pri | Gap                              |
|--------|------------------------------------|-----|----------------------------------|
| #XX    | Vague feature request              | —   | No clear outcome, needs product decisions |

## Not Suitable for Overnight
| Issue  | Title                              | Pri | Reason                           |
|--------|------------------------------------|-----|----------------------------------|
| #XX    | UI redesign with open questions    | ▲   | Needs product decisions           |
```

For split candidates, note them in the "Ready" bucket with a "(split recommended)" tag and explain the proposed split.

### 4. Confirm with User

Ask the user which issues to label as "overnight" on GitHub. Use `AskUserQuestion` with the ready candidates as options (multiSelect: true).

### 5. Apply Labels

For confirmed issues, use the `gh` CLI to add the "overnight" label:

```bash
gh issue edit <number> --add-label "overnight"
```

If splits were approved, create the sub-issues first, then label the backend one.

### 6. Hand Off Preppable Issues

If any issues landed in the "Preppable" bucket, suggest:

> **Prep these for overnight?** Run `/zv01.6-prep-overnight #XX #YY` to autonomously build exploration + plan artifacts. After that, they'll be ready for tonight's batch.

Include the exact command with issue IDs so the user can copy-paste.

## Notes

- Don't re-assess issues already labeled "Overnight" — just note they're already queued
- If no good candidates exist, say so honestly. Don't force it.
- Issues with no description or only a title → "Needs Scoping First"
