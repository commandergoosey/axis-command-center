# Codex Fit — Assess Issues for Codex Lunch-Runner

Evaluate open GitHub issues against the Codex lunch-runner's constraints and recommend which to batch into a `run-codex-issues.sh` session.

## Context: How the Lunch-Runner Works

The lunch-runner (`scripts/run-codex-lunch.sh`) executes tasks via Codex CLI in isolated worktrees with `--full-auto` sandbox. Every task goes through:
1. Codex execution (prompt → code changes)
2. Post-execution scope check (hard-deny + safe-allowlist enforcement)
3. Verification loop (typecheck + vitest + lint:colors, up to 3 retries with fix prompts)
4. Commit + PR

**If a task touches anything outside scope, it's rolled back and failed.** This is non-negotiable.

### Scope Policy (from `scripts/run-codex-lunch.sh` + `scripts/lib/scope.mjs`)

**HARD-DENY** (instant fail if touched):
- `scripts/`, `.github/`, `.claude/`, `.husky/`
- `supabase/migrations/`
- `next.config`, `vercel.json`, `tsconfig*.json`, `eslint.config`, `vitest.config`, `playwright.config`
- `.env*`, `AGENTS.md`, `CLAUDE.md`, `package.json`, `package-lock.json`
- `.gitignore`, `.cursorrules`, `.windsurfrules`
- `src/types/database.types.ts` (autogenerated)

**SAFE-ALLOWLIST** (only these paths are permitted):
- `src/` (application source)
- `docs/`, `tests/`, `test/`, `e2e/`
- `ai/zv/`
- `supabase/seed.sql`, `README.md`, `OPS.md`

**Cross-section tolerance**: up to 2 out-of-scope files with <=30 changed lines total.

### Sections (from `scripts/lib/scope.mjs`)
Each task is scoped to a section. Cross-section changes are tolerated only within tight limits.
- **api**: `src/app/api/**/*.ts`
- **map**: map components, canvas hooks, map lib, aerial, events
- **lib**: `src/lib/**` (excluding map/editing)
- **pages**: dashboard pages, auth pages
- **components**: shared UI (excluding map/events/aerial)
- **shared**: types, contexts, core hooks (useAuth, useSite, useJob*, etc.)

## Your Task

### 1. Fetch Open Issues

Use `gh` CLI to fetch all open issues for the current project (AXIS Command Center). Apply the same filters as `/zv01-triage`:
- Exclude `project: CPRE` labels
- Exclude `codex-overnight` labels
- Exclude issues already labeled `overnight`
- Exclude issues with `status: in-progress` or `status: in-review`

### 2. Assess Each Issue (Parallel Subagents)

Launch **parallel Explore subagents** — one per issue (or batch 2-3 per agent if >10 issues). Each agent receives:
- Issue number, title, body (via `gh issue view N`)
- The scope policy above
- The 6 fitness criteria below

**Codex Fitness Criteria** — score each 0-2:

| # | Criterion | 2 (green) | 1 (yellow) | 0 (red) |
|---|-----------|-----------|------------|---------|
| A | **Scope compliance** | Only touches safe-allowlist paths | Touches 1-2 protected files that could be worked around | Requires hard-deny paths (migrations, scripts/, config) |
| B | **Mechanical vs Creative** | Pure pattern: refactor, extraction, lint fix, test addition | Some judgment calls but bounded (e.g., pick between 2 clear approaches) | Architecture decisions, UX design, domain expertise |
| C | **Bounded scope** | Specific files listed, clear acceptance criteria | General area described, reasonable to infer files | Vague ("improve X"), open-ended exploration |
| D | **Testable by verification** | Changes caught by typecheck + vitest + lint:colors | Partially testable (typecheck yes, but needs manual visual check) | Untestable (visual-only, behavior-only, needs browser) |
| E | **Size** | <200 LOC estimated | 200-500 LOC estimated | >500 LOC estimated |
| F | **Self-contained** | No deps on other issues, no new npm packages | Needs a new package but it's standard | Depends on other issue shipping first, or needs external service setup |

Each agent returns:
```json
{
  "issue": 123,
  "title": "...",
  "scores": { "A": 2, "B": 2, "C": 1, "D": 2, "E": 1, "F": 2 },
  "total": 10,
  "verdict": "SEND | MAYBE | SKIP",
  "section": "api | map | lib | pages | components | shared | multi",
  "blockers": ["needs migration", "touches package.json"],
  "estimated_loc": 150,
  "reason": "One-line rationale"
}
```

**Verdict thresholds:**
- **SEND** (10-12): All green or mostly green, no red on A (scope) or F (deps). Ship it.
- **MAYBE** (7-9): Workable with minor prompt engineering. Note what to watch.
- **SKIP** (0-6): Too creative, too big, or scope-blocked. Needs human session.

Show a **single sorted table** (SEND first, then MAYBE, then SKIP):

### 4. Generate Lunch-Runner Command

For all SEND issues, generate the ready-to-paste command:

```bash
scripts/run-codex-issues.sh --issues "398,399,153" --skip-push
```

Also generate a `--dry-run` variant for preview.

### 5. Note MAYBE Issues

For MAYBE issues, explain what would make them SEND-ready:
- Can the scope be narrowed? (e.g., "skip the config change, just do the src/ part")
- Can it be split? (e.g., "migration piece is SKIP, but the hook refactor is SEND")
- Is there a prompt trick? (e.g., "explicitly tell Codex to NOT touch package.json")

### 6. Recommend Batch Size

Based on the SEND count, recommend:
- **1-3 issues**: Run all in one `run-codex-issues.sh` call
- **4-6 issues**: Split into 2 batches to manage worktree load
- **7+**: Prioritize top 4-5 by score, defer the rest

## Important Notes

- **Do NOT assess issues that are already in-flight** (labeled `status: in-progress` or with open PRs)
- **Do NOT include issues the user is already running in a pipeline** — ask if unclear
- **If an issue scores SEND but touches multiple sections**, flag it — cross-section tasks have higher failure rates
- **Database migrations are an automatic SKIP** — Codex cannot run `supabase db push` and `database.types.ts` is hard-denied
- **New npm packages are a yellow flag** — they require `package.json` changes which are hard-denied. The task can still SEND if the package is already installed or if the code change works without it.
