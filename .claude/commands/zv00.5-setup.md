# Project Setup & CTO Configuration

Set up the project for the ZV workflow: emit (or repair) the project `CLAUDE.md` with the four load-bearing lines global skills depend on, generate a CTO rule file, create working directories, and verify GitHub CLI integration.

## Why this skill exists

Global ZV / pipeline / codex skills discover project-specific paths by grepping the project's `CLAUDE.md` for fixed prefixes at column 0:

```
External wiki: ...
Session log: ...
DB migration convention: ...
Label schema: ...
```

If those lines are missing or phrased differently, skills fall back to hardcoded fork paths — which either don't exist in a new project, or (worse) point at somebody else's repo. This skill's job is to guarantee the four lines are present and grep-able before the user runs anything else.

The contract vocabulary lives in `~/.claude/templates/CLAUDE.md`. Treat that file as the source of truth for acceptable values.

## Your Task

### 1. Detect Project Stack
Read `CLAUDE.md`, `package.json`, `requirements.txt`, `Cargo.toml`, `go.mod`, `pyproject.toml`, or whatever dependency/config files exist. Identify:
- Project name (from `package.json` `name`, repo directory name, or ask)
- Frontend framework & UI library
- State management
- Backend / database
- APIs / external services
- Payments, analytics, auth providers
- Any code-assist agents or CI/CD tools mentioned

### 2. Detect the Four Contract Values

Do not ask the user these questions upfront — detect first, then confirm.

- **External wiki:** if `./docs/` exists with more than a README, default to `in-tree docs/`. Else check if a sibling `<repo>-knowledge/` directory exists at `~/projects/` and default to that path. Else default to `in-tree docs/` and create `./docs/` in step 6.
- **Session log:** pair with External wiki — `in-tree docs/log.md` for in-tree, `<wiki-root>/log.md` for external.
- **DB migration convention:** detect in this order
  - `supabase/migrations/` exists → `supabase (supabase/migrations/)`
  - `prisma/schema.prisma` exists → `Prisma (prisma/migrations/)`
  - `drizzle.config.*` exists → `Drizzle (drizzle/)`
  - `alembic.ini` exists → `Alembic (alembic/versions/)`
  - `better-sqlite3` in `package.json` or a `schema.ts` file containing `SCHEMA_VERSION` → `SQLite + SCHEMA_VERSION bump in <detected-path>`
  - none of the above → `no DB layer`
- **Label schema:** run `gh label list --limit 100 2>/dev/null`; if `P1-urgent` and `status: backlog` are both present → `ZV workflow labels`. Else → `project-specific — see gh label list`.

### 3. Ask to Fill Stack Gaps
For anything you couldn't detect in step 1, ask the user in a single concise message. Don't ask about things you already found. Typical gaps:
- Payment provider
- Analytics provider
- Auth approach
- Anything non-obvious from config files

Then present the four contract values you auto-detected in step 2 and ask the user to confirm or override. Example:

```
Detected contract values:
- External wiki: in-tree docs/
- Session log: in-tree docs/log.md
- DB migration convention: SQLite + SCHEMA_VERSION bump in src/lib/db/schema.ts
- Label schema: ZV workflow labels

Confirm or override (e.g. "change External wiki to ~/projects/foo-knowledge/wiki/")?
```

### 4. Generate CTO Rule File
Write `.claude/rules/cto-workflow.md` in the current project directory. Use this structure:

```
# CTO Workflow

**What is your role:**
- You are acting as the CTO of [PROJECT NAME], a [brief tech stack description].
- You are technical, but your role is to assist the user (head of product) as they drive product priorities. You translate them into architecture, tasks, and code reviews.
- Your goals are: ship fast, maintain clean code, keep infra costs low, and avoid regressions.

**We use:**
[Detected + confirmed stack, organized by category]

**How to respond:**
- Act as the CTO. Push back when necessary. Do not need to be a people pleaser. Need to make sure we succeed.
- First, confirm understanding in 1-2 sentences.
- Default to high-level plans first, then concrete next steps.
- When uncertain, ask clarifying questions instead of guessing. This is critical.
- Use concise bullet points. Link directly to affected files / DB objects. Highlight risks.
- When proposing code, show minimal diff blocks, not entire files.
- When SQL is needed, wrap in sql with UP / DOWN comments.
- Suggest automated tests and rollback plans where relevant.
- Keep responses under ~400 words unless a deep dive is requested.

**Our workflow:**
1. Brainstorm on a feature or discuss a bug to fix
2. Ask all clarifying questions until sure of understanding
3. Create a discovery prompt gathering all needed information (file names, function names, structure)
4. Once codebase context is gathered, ask for any missing information needed manually
5. Break the task into phases (if not needed just make it 1 phase)
6. Create prompts for each phase, with status reports on changes in each phase to catch mistakes
7. Execute phases and review status reports
```

### 5. Emit or Repair Project CLAUDE.md

Read `~/.claude/templates/CLAUDE.md` — that is the source of truth for the contract section and its value vocabulary.

**Case A — no CLAUDE.md in project:** copy the template verbatim, then substitute the `{{PLACEHOLDERS}}` with detected/confirmed values from steps 1–3.

**Case B — CLAUDE.md exists but is missing the `## ZV Workflow Contract` section (or one of the four lines):** do NOT rewrite the whole file. Append a new `## ZV Workflow Contract` section at the end using the exact structure from the template (header + intro paragraph + four lines + vocabulary subsection), with the detected/confirmed values. If the section exists but one line is missing, add only the missing line(s) under the existing section.

**Case C — CLAUDE.md exists and already has all four lines:** leave it alone. Print a "contract already present, skipping" note.

### 6. Create ZV Working Directories
Create the following directory tree (skip any that already exist):
```
ai/zv/plans/
ai/zv/explorations/
ai/zv/reviews/
ai/zv/changelogs/
ai/zv/retros/
```

If External wiki is `in-tree docs/` and `./docs/` does not yet exist, also create `./docs/` and touch `./docs/log.md`.

### 7. Verify GitHub CLI Connection
```bash
gh auth status
```

If not authenticated, tell the user to run `gh auth login`.

### 8. Lint the Contract

Run these four greps against the project `CLAUDE.md`. The regex tolerates both the column-0 canonical form (`External wiki: ...`) and the bolded-prefix form (`**External wiki:** ...`) — both forms are tolerated. The template emits the column-0 form because it is easier to grep mechanically.

```bash
grep -En '^(\*\*)?External wiki:(\*\*)? ' CLAUDE.md
grep -En '^(\*\*)?Session log:(\*\*)? ' CLAUDE.md
grep -En '^(\*\*)?DB migration convention:(\*\*)? ' CLAUDE.md
grep -En '^(\*\*)?Label schema:(\*\*)? ' CLAUDE.md
```

Each must return at least one line. If any returns zero lines, fail loudly — print which prefix(es) are missing and ask the user to resolve before continuing. Do not proceed to step 9 on failure.

Also verify against the value vocabulary: the right-hand side of each line must match one of the accepted values from `~/.claude/templates/CLAUDE.md` (or be a recognizable variant — e.g. a specific SQLite schema path is fine). Print a warning (not a hard fail) if a value looks unusual.

### 10. Confirm
Show the user:
- Path to the generated CTO rule file
- Path to the project CLAUDE.md (new or updated)
- The four contract values that were written
- Lint result (PASS / WARN / FAIL)
- Any follow-up actions the user needs to take (e.g. "create `~/projects/<project>-knowledge/` if you chose external wiki")
